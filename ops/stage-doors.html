01

How to read this

Every mockup below is real HTML at real proportions in the shipping design system, not a picture of an idea. Where a figure appears it is a figure the site already publishes, so you are looking at what the door would actually say on the day it opened.

Two or three per door

Variants differ in what the door leads with — a tool, a question, or a price — not in color. If two variants would produce the same page with different padding, only one is here.

A recommendation, with the cost of it

Every variant carries what it buys and what it costs, and one is marked. A mockup set without a recommendation just moves the decision back to you, which is not help.

Then the part that decides the timeline

Section 09 is the impact list: the registry field, the six passes that change, the one configuration line that would make all five hubs invisible, and the two ways this ships broken.

One thing in the first proposal is now out of date

The coverage audit recorded “Stage 2, in a program — 0 pages, hold”. That was true on 10 August. The practicum page and the career-change page shipped on the 11th, so the student door now has two pages of its own plus the 78 program pages and the placement dataset behind it. Four of the five doors can open; only the practice-owner door still fails the test.

What it buys

The highest-utility artifact on the whole site for this reader: it can be screenshotted and taken into a placement meeting. The no-private-practice rule in particular saves people a wasted month.

What it costs

Entirely static, nothing personalized, and it will be read once. It is a great module and a weak hero.

The call

The lookup is what gets the link shared; the rules card is what gets it saved. Putting them in that order means the door earns its traffic and then earns the bookmark. 2B’s 90-day countdown is important enough to appear but not distinctive enough to lead — and building it as a frame would duplicate door 1.

09

What else changes

Five hub pages is the small part. This is the rest of it, in the order things would break.

The one that would waste a day

Every pass in _dev/ walks the site root plus SUBDIRS, which is ("money", "licensure", "getting-paid", "practice", "training"). A new top-level /for/ directory is invisible to all of them — no chrome, no nav, no analytics, no CSS extraction — and invisible to discovery.py, so the hubs would also be missing from the sitemap.

The five hubs would build, look completely unstyled, and every guard would still report clean, because each guard checks its own pass and nothing checks the set of directories. Add "for" to SUBDIRS in the same commit that creates the directory.

The data model — one field, and one guard that has to be strict

Two keys per registry entry, alongside the existing topic:

"stages": ["associate", "student"],
"stage_note": {
  "associate": "What the claim is worth, and the 30-day clock.",
  "student": "Why a placement cannot ask you to work unpaid."
}

stage_note must be mandatory wherever stages has an entry. It is the only thing standing between a stage hub and a re-listed topic hub, and an optional field will be skipped on the pages where writing it is hardest — which are the pages that need it most.

The two ways this ships broken

1. Thin duplicates. A stage hub that is 90% the same list as a topic hub is a thin page, and five of them pointed at overlapping content is the classic way a site loses ground it already held. stage_note is the entire mitigation: every listing has to say something the topic hub does not. Guard it, do not trust it.

2. Stale duplicates. This repo has shipped a stale-duplicate bug three times — double-escaping twice and the CIIS tuition card. Any figure appearing on both a hub and a leaf must be read from the same data module at build time, never written into the hub. If a number is typed into a hub, it is already wrong.

10

Build order

Revised from the first proposal, because the student door opened. Each step is shippable on its own and the site is never half-migrated.

  1. Add "for" to SUBDIRS, and tag the library

    The configuration line first, so nothing built afterward is invisible. Then stages and stage_note across ~200 entries, with the mandatory-note guard written before the tagging rather than after.

    No new pages. Registry is ready and nothing is live yet.

  2. /for/associates/ — variant 3C

    Loudest room, twelve pages ready, and the ledger is the cheapest of the three to build because the arithmetic already exists in the 3,000-hour calculator.
